# 2.5 Control panel & live status (`:65000`)

*What this covers: the browser control panel served while the loop is up — driving turns without speaking, mute/PTT, the live token/context status block, and its loopback-only default.* · Runbook index: [`README.md`](README.md)

When the loop is up it also serves a **control panel** at `http://<host>:65000/` (startup log prints `[control] web box → …`; port overridable with the `WEB_PORT` env var). Open it in a browser on the same machine. It lets you **drive turns without speaking** — built for quiet/shared rooms and long soak sessions.

**Controls:**
- **Text turn** — type + Enter (or Send). Injected as a user turn (bypasses mic/STT); if the companion is mid-reply it interrupts (text barge-in). Nothing registers until you submit, so you can edit freely first.
- **Mute mic** — latched toggle. Mutes the mic *before VAD* so a muted mic can't trigger barge-in or a half-open turn; the process keeps running and **text still works while muted**. Spoken input resumes on Unmute.
- **PTT (hold)** — momentary override: hold the button (or hold **M** while the page is focused) to open the mic, release to return to the latched baseline. Works from either baseline.
- **`MIC:` indicator** — always shows `LIVE (baseline)` / `MUTED (baseline)` / `OPEN (PTT held)`. The Mute toggle *is* the baseline; PTT is a temporary override.
- **Record** — capture the session to disk (M7). Always records the companion's voice (TTS); tick **my mic** and/or **background music** to add those stems. Press again to stop.

**Endpoints** (all local, JSON): `POST /say {text}`, `POST /mute {muted}`, `POST /ptt {down}`, `POST /record/start {name?, mic?, music?}`, `POST /record/stop`, `GET /record/status`, `GET /usage` (per-turn counts), `GET /engine` (model/capacity, and whether the server serves the configured model), `GET /memory` (read-only memory status: mode, backend, per-turn switches, recall attribution — names and counts only, never content), `POST /memory/per-turn-voice {on}` (the one runtime memory knob — see the Memory line below). `GET /route` (where this conversation's audio is: the desk or a paired device, its network path and buffer depth — names and numbers only). `GET /presence` (the talk's presence state for a reader beside Hearth — `bot_speaking`, `user_speaking`, `muted`, `ts`; state only, no words, and the one route another app's page may read). Each POST logs a `[control] …` line.

**Live token/context status block** — monospace lines below the input:
```
Tokens | <held> [<%> of <reliable> reliable] · <to line> · advertised <n> · model max
Engine | Inference Provider · Model ID · hands: off|none|read-only|write-in-class|full
Agent  | Name: <character> · Voice: <voice>
Misc   | Session · Remembering: on|off · Keeping: on|off (— = memory not configured) · net turn growth · total tok. xmitted
Memory | <backend> · per-turn: chat|chat + voice|off · recalled: <n> at open via <backend> · last turn: <n> extra(s) via <backend>
⚠ approaching reliable context line — …   ← appears only in the warn/over zone
⚠ The model server is serving <x> — this conversation was set up for <y>. …   ← only on a mismatch
```
The **mismatch line** is the one thing on the block that says the conversation is not on the
model you chose: the model server serves one model, and picking another row on the launch page
does not change what it serves until that row is applied and loaded (Models card: Apply, then
Load). The facts ride `/engine` as `served_model`, `configured_model` and `model_match`
(`null` = the server did not answer; unknown is not a mismatch), refreshed every 60 s along
with the engine facts, so a door reloaded under a sitting — or a live switch to another row —
shows within a minute. The Engine line carries a short `⚠ not the configured model` tag at the
same time.
The Engine line's **`hands:`** item says what this character may dispatch to an OpenClaw agent: `off` when
`config/openclaw.toml` is off, otherwise the tier from the character's own `characters/<c>/capabilities.toml`
— `none` (the default for a character with no grant file, meaning the bridge is on but no tools were
registered for this one) or the granted word. Resolved once at startup, like the rest of the Agent facts.
The **`Memory`** line appears only when a memory seam is attached this sitting (the switches alone
always show on `Misc`). It is a **read-only tap** (`GET /memory`, polled every 5 s): the active
backend (with a `(not keeping)` marker when nothing will be retained), the per-turn recall switches,
and the last recalls' **honest attribution** — each names the backend that *actually answered*, so
a floor fallback shows as `floor`, never masquerading as the primary. Names and counts only —
recalled text, your words, and the cue never ride this route. All memory *writes* (curation, mode
changes) live behind Hearth's token door, not here — with **one runtime knob** as the sanctioned
exception: a **pause/resume voice recall** button on the Memory line (`POST /memory/per-turn-voice
{on}`). It is a **runtime-only poke** of the live seam's voice switch — per-turn recall burns context
every turn, and this stops the burn mid-sitting (effect next turn; already-applied extras are
cleared too). No file is written: `config/memory.toml` stays the between-sessions truth, and a
restart or live switch returns to it. The button only appears when the sitting *started* with
`[memory.per_turn].voice` on (the prefetch processor is built at companion start — a voice-off sitting
has nothing to light, and the route says so with a 409 naming the fix).
`held` = the context the model holds *this turn* — the last request's prompt *plus its reply* (window occupancy, not cumulative). At open / resume / live switch it carries an **`est.` marker** (chars/4 seed over the pre-fill — system prompt, memory block, any restored transcript) until the first turn's server report replaces it. The gauge now measures against a **reliable-usable line** (`reliable` = the measured usable ceiling, `128,000` today), NOT the advertised window — so you see the *usable* wall coming. Watch **`to line`** (reliable budget remaining) tick down; the `Tokens` line **recolors and warns before the wall**:

| Zone | `held ÷ reliable` | Look |
|---|---|---|
| **ok** | `< 75%` | normal blue |
| **warn** | `75–100%` | amber + the `⚠ approaching reliable context line` banner |
| **over** | `≥ 100%` | red/bold + banner |

When you hit **warn**, wrap up or restart (a fresh session resets `held`). `advertised` (the context the server actually allocated) and `model max` are shown as references. If `reliable_context` isn't set for the model, the gauge falls back to gauging against `advertised`. The **`Agent`** line names the active persona — `character` + `voice`, resolved once from `config/active.toml` at startup (static; falls back to `—` if unresolved). `net turn growth` = how much the last turn added; `total tok. xmitted` = cumulative input this session. Capacity + Model ID come from an **engine probe** at startup, chosen by `LM_PROVIDER`: on the default `llama-server` it reads the server's native `GET /props` (allocated context from `default_generation_settings.n_ctx`; the GGUF filename as the model id — `llama-server` doesn't expose `--alias` there, and it reports no train-time maximum, so `model max` stays `—`). *If you use LM Studio* (`LM_PROVIDER=lmstudio`) it reads that app's native `/api/v0/models` instead, which supplies both the loaded and the maximum context. Either way, if the probe is unreachable the block shows `—` and the loop runs fine regardless.

> **Loopback only by default.** Binds to `127.0.0.1:65000`. To reach it from a phone on the LAN, launch with **`WEB_HOST=0.0.0.0`** set (e.g. `WEB_HOST=0.0.0.0 ./start.sh`) — that exposes text-inject/mute/PTT **plus the read-only status block (Model ID + aggregate token counts — no conversation content)** to every device on the network. **Owner opt-in**, not a default ("sensitive text stays local").

## Editing the pages (`HEARTH_DEV_RELOAD`)

Every page — this panel and Hearth's six — is read from disk **once, at import**, and
served from that string. No request touches the disk, the bytes cannot change under a running
process, and a page that fails to build (a lost placeholder, say) takes the process down at
startup instead of 500-ing one request at a time. The cost is that a one-character CSS change
means restarting the companion (for this panel) or Hearth (for the others).

Three **shared** files are spliced into pages at import, each with a divergence-guard test:
`ui/brand.css` (palette, mark, header — all six pages), `ui/switch_card.js` (the companion
switcher — the panel and the launch page), and `ui/admin_shell.js` (the `$`/`el` helpers, the
access key in localStorage, the authed `api()`, `show`/`report`, token entry, the poll loop — the
four authed Hearth pages). The pairing page takes only the brand layer: it is what a device
*without* the access key opens, so a shell that carries the access key has nothing for it.

Nineteen more are **page sections** — not a shared layer, just seams, so that a knob edit and a
meter edit stop being edits to the same file. Five pages have them. Each keeps its markup and
the state every section reads; the jobs live beside it, declared in a `ui/*_sections.py`:

| Page | Sections |
|---|---|
| `control_page.html` | `ui/panel_style.css` (its own skin — the shared palette still arrives via `brand.css`) · `panel_record.js` (session recording) · `panel_status.js` (the status block and its three poll timers) · `panel_knobs.js` (help text, sliders, profile buttons) · `panel_manual.js` (the rail and the manual reader) · `panel_turn.js` (the turn meter) |
| `roster_page.html` | `ui/roster_onboard.js` (the onboarding wizard) · `roster_edit.js` (persona editor + add-a-voice) · `roster_fork.js` (the branch card) |
| `settings_page.html` | `ui/settings_schema.js` (walking pydantic's JSON Schema) · `settings_files.js` (the file list) · `settings_form.js` (the generated form) · `settings_confirm.js` (preview-then-confirm) |
| `first_run_page.html` | `ui/firstrun_check.js` (step 1 — is the server answering, which model) · `firstrun_listen.js` (steps 2 and 3 — the start and the first words) |
| `launch_page.html` | `ui/launch_poll.js` (the state poll and every card it flips) · `launch_deferred.js` (a Start held behind someone else's maintenance lock) · `launch_devices.js` (the audio route control and the forget flow) · `launch_stop.js` (the Stop card: its words, its countdown, its wiring) |

They land inside the page's own `<script>` block, so they share one scope — which means a name
declared twice is a browser `SyntaxError`. `panel_status.js` reads a `let` that
`panel_knobs.js` declares; that survives any placeholder order today only because the read
happens after an `await`, so the written order is pinned to keep it from quietly becoming
load-bearing. `tests/test_page_sections.py` fails if any of that stops being true — for this
page and for the roster, settings, first-run and launch pages, which are split the same way. Adding a section? Add
a file, not another inline block.

Set **`HEARTH_DEV_RELOAD=1`** on the process you're working on and every read goes back to disk
instead, shared files included — so an edit to any of them lands on a browser refresh. In exchange, a malformed edit becomes a 500 on that refresh
rather than a startup failure. Default off; the flag is read once at startup, so a production
process cannot drift into it.

```sh
HEARTH_DEV_RELOAD=1 ./start.sh          # the panel at :65000
HEARTH_DEV_RELOAD=1 python -m hearth.serve   # the facade's pages at :65001
```
